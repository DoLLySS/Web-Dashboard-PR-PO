# คู่มือสร้าง Power Automate Flow ทีละขั้น (S4)

เขียนสำหรับ: ผู้ดูแล Microsoft 365 / IT ที่สร้าง Flow ได้ แต่ **ไม่ต้องรู้โค้ดของแอป**
อ้างอิงโค้ด: `utils/power_automate_api.py` และ `utils/masterlist_client.py` (ณ commit ที่ระบุใน `00_SUMMARY.md`)

> **สถานะ:** รูปแบบคำขอ/คำตอบในคู่มือนี้ตรงกับที่โค้ดแอปส่งและรับจริง แต่ **ยังไม่เคยทดสอบกับ Flow หรือ SharePoint จริงเลย** (ทดสอบกับ Flow ปลอมเท่านั้น) ชื่อเมนู/ปุ่มของ Power Automate เปลี่ยนตามรุ่น ให้ถือเป็นแนวทาง ถ้าหน้าจอไม่ตรงให้ยึดความหมายของแต่ละขั้น
>
> **กล่อง "รอ IT ตอบ"** ในเอกสารนี้ คือส่วนที่ยังตัดสินใจไม่ได้จนกว่า IT จะตอบ `02_S0_IT_REQUEST.md` ข้อ 6 (ปลายทาง Master-List เป็นอะไร) อย่าลงมือส่วนนั้นก่อนมีคำตอบ

## 0. ก่อนเริ่ม

| เรื่อง | ต้องมี |
|---|---|
| สิทธิ์ | ใบอนุญาตที่ใช้ HTTP trigger ได้ (ปกติเป็น Premium) ตรวจกับนโยบาย tenant ตามข้อ 1 และ 4 ของ `02_S0_IT_REQUEST.md` |
| เจ้าของ Flow | บัญชีบริการหรือกลุ่ม ไม่ใช่บุคคล และ connection เขียน SharePoint ได้ |
| ที่ทดสอบ | **ไลบรารีเอกสารที่ว่าง** (Flow 1) และ **รายการ/ไฟล์ทดสอบที่ว่าง** (Flow 2) ห้ามทดสอบกับของจริง |
| ความลับ | URL ของ Flow มีลายเซ็นลับในตัว ถือเป็นรหัสผ่าน ส่งให้ผู้ดูแลแอปทางช่องทางลับเท่านั้น (ไม่ใช่อีเมลทั่วไป/แชต/ใน Git) |

Flow ที่ต้องสร้าง **2 ตัว แยกกัน แต่ละตัวมี URL ของตัวเอง**:

| Flow | ทำอะไร | ค่าใน `.env` ฝั่งแอป |
|---|---|---|
| Flow 1 ส่งไฟล์ | รับไฟล์ทีละไฟล์ สร้างโฟลเดอร์และไฟล์ในไลบรารี SharePoint ตอบลิงก์ | `POWER_AUTOMATE_UPLOAD_URL` |
| Flow 2 ส่งแถว Master-List | รับข้อมูล 1 แถว บันทึกลงปลายทาง ตอบ `{"ok": true}` | `MASTERLIST_API_URL` |

แอปส่งทีละคำขอ ไม่ขนาน และมี 2 ตัวนี้เป็นอิสระต่อกัน ถ้า Flow 2 ล้ม แถวและไฟล์ในเครื่องยังบันทึกครบ

## 1. Flow 1: ส่งไฟล์เข้า SharePoint

### 1.1 Trigger

1. สร้าง Instant cloud flow เลือก trigger **When an HTTP request is received**
2. ตั้ง "Who can trigger the flow?" ตามนโยบายของ tenant (ต้องเลือกที่แอปบนเครื่องภายนอก Microsoft 365 เรียกได้ และเอกสาร Microsoft ปัจจุบันระบุตัวเลือกไว้ ให้ตรวจก่อน)
3. ใส่ Request Body JSON Schema ตามนี้ (ตรงกับที่แอปส่ง):

```json
{
  "type": "object",
  "properties": {
    "requestId":     { "type": "string" },
    "folderParts":   { "type": "array", "items": { "type": "string" } },
    "fileName":      { "type": "string" },
    "contentBase64": { "type": "string" },
    "sha256":        { "type": "string" }
  },
  "required": ["requestId", "folderParts", "fileName", "contentBase64", "sha256"]
}
```

ตัวอย่างคำขอจริง (ค่าสมมติ):

```json
{"requestId": "3f2b8c1e-5a7d-4c9e-8b21-0d6e4f7a9b13",
 "folderParts": ["2026", "Mar", "19", "ตัวอย่างโฟลเดอร์"],
 "fileName": "ตัวอย่าง.pdf",
 "contentBase64": "JVBERi0x...",
 "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"}
```

- `folderParts` คือโฟลเดอร์ซ้อนชั้น เรียงจากนอกเข้าใน (ปี / เดือน / วัน / ชื่อ) สร้างภายใต้โฟลเดอร์รากที่ IT กำหนด
- `fileName` ผ่านการทำความสะอาดแล้ว (อักขระต้องห้ามของ SharePoint ถูกแทนด้วย `_` ภาษาไทยคงเดิม) Flow ไม่ต้องแก้ชื่อซ้ำ
- `sha256` คือค่า sha256 (hex พิมพ์เล็ก) ของเนื้อไฟล์ **ก่อน** เข้ารหัส base64
- ขนาดไฟล์ที่แอปยอมส่ง 50 MB (ปรับได้ที่ `POWER_AUTOMATE_MAX_FILE_MB`) base64 ใหญ่ขึ้นราว 1/3 ต้องเทียบกับเพดานขนาดคำขอและเวลาตอบของ Flow ตามข้อ 5 ของ `02_S0_IT_REQUEST.md` ถ้าเพดานต่ำกว่า ให้ลด `POWER_AUTOMATE_MAX_FILE_MB` ให้ไม่เกินเพดานนั้น (แอปยังไม่รองรับการแบ่งส่งเป็นชิ้น)

### 1.2 ตั้งค่า Flow ก่อนเพิ่มขั้นตอน

- **Concurrency control** ของ trigger: เปิดและตั้งจำนวนเป็น **1** (Settings ของ trigger) เพื่อให้การเช็กซ้ำด้วย `requestId` ไม่ชนกันเมื่อมีสองคำขอเข้าพร้อมกัน
- เปิดการแจ้งเตือนเมื่อ Flow ล้มเหลว (ส่งอีเมลหาผู้ดูแล)
- ตั้ง Run-only users / การแชร์ ให้เจ้าของเป็นบัญชีบริการ/กลุ่ม

### 1.3 ขั้นตอนใน Flow (ตามลำดับ)

| # | Action | ทำอะไร | ถ้าไม่ผ่าน |
|---|---|---|---|
| 1 | Condition ตรวจ header | ถ้าจะใช้ `X-Api-Key`: ค่า `triggerOutputs()['headers']['X-Api-Key']` ต้องเท่ากับคีย์ที่ตกลงกัน (เก็บคีย์ใน environment variable/Key Vault ไม่ฝังในขั้นตอนถ้าทำได้) | Response **401** `{"error":"unauthorized"}` แล้วจบ |
| 2 | ตรวจ `requestId` ซ้ำ | ดูหัวข้อ 3 ด้านล่าง ถ้าเคยทำสำเร็จแล้ว ให้ตอบ **ลิงก์เดิม** ด้วย Response 200 แล้วจบ ไม่สร้างไฟล์ซ้ำ | ไม่ซ้ำ → ไปต่อ |
| 3 | ตรวจ sha256 | แปลง `contentBase64` เป็นไบนารีด้วย `base64ToBinary(...)` แล้วคำนวณ sha256 เทียบกับ `sha256` ที่ส่งมา (ทำได้ด้วย action คำนวณ hash ที่ tenant อนุญาต หรือข้ามขั้นนี้ถ้าทำไม่ได้ แต่ต้องจดว่าข้ามไว้) | Response **400** `{"error":"sha256 ไม่ตรง"}` |
| 4 | สร้างโฟลเดอร์ซ้อนชั้น | ไล่สร้างตาม `folderParts` ทีละชั้น (Apply to each ตามลำดับ ห้ามขนาน) **ต้องลองจริงว่าสร้างโฟลเดอร์ที่มีอยู่แล้วเกิด error หรือไม่** แล้วจัดการ (เช่น เช็กก่อนสร้าง หรือ Configure run after ให้ข้าม error ประเภท "มีอยู่แล้ว") | Response **500** `{"error":"สร้างโฟลเดอร์ไม่สำเร็จ"}` |
| 5 | Create file | สร้างไฟล์ในโฟลเดอร์ปลายทาง ชื่อ `fileName` เนื้อหา `base64ToBinary(triggerBody()?['contentBase64'])` | Response **500** `{"error":"..."}` |
| 6 | บันทึก `requestId` | เขียน `requestId` + `fileUrl` ลงที่เก็บกันซ้ำ (หัวข้อ 3) | ล้มก็ยังตอบสำเร็จได้ แต่แจ้งเตือนผู้ดูแล |
| 7 | Response 200 | ตามรูปแบบหัวข้อ 1.4 | |

ข้อควรระวัง:
- ชื่อไฟล์ซ้ำในโฟลเดอร์เดียวกัน: ตัดสินใจกับ IT ว่าทับหรือปฏิเสธ แอปตั้งชื่อให้ไม่ซ้ำฝั่งเครื่อง (`ชื่อ_1.pdf`) แต่ไม่รู้ว่าฝั่ง SharePoint มีอะไรอยู่แล้ว
- ห้ามเก็บเนื้อไฟล์หรือ `contentBase64` ใน run history ถ้าตั้งได้ (เปิด Secure inputs/outputs ของ action ที่เกี่ยวข้อง) เพราะเป็นเอกสารจริง

### 1.4 Response

ใช้ action **Response** ตั้ง Header `Content-Type: application/json`

สำเร็จ (Status 200):

```json
{"fileUrl": "https://<ตัวอย่าง>.sharepoint.com/sites/<site>/<library>/2026/Mar/19/ตัวอย่าง.pdf",
 "folderUrl": "https://<ตัวอย่าง>.sharepoint.com/sites/<site>/<library>/2026/Mar/19"}
```

ล้มเหลว: ตอบสถานะ 4xx/5xx พร้อม `{"error": "ข้อความสั้น ๆ"}` (หรือ 200 พร้อม `error` ก็ได้ แอปถือเป็นล้มเหลวทั้งสองแบบ)

กติกาที่แอปใช้ตีความ:
- **สำเร็จ** เมื่อมี `fileUrl` เป็นลิงก์ `http(s)` เท่านั้น (`folderUrl` ไม่บังคับ)
- ข้อความ `error` ควรสั้น ไม่เกิน 200 ตัวอักษร ไม่มี URL/คีย์/ข้อมูลภายใน (แอปตัดทอนและซ่อนค่าลับที่สะท้อนกลับ แต่ไม่ควรพึ่ง)
- Response ต้องเล็ก (แอปไม่รับเกิน 64 KB)
- อย่าตอบ redirect (3xx): แอปไม่ตาม

### 1.5 สิ่งที่แอปทำเมื่อ Flow 1 ตอบแบบต่าง ๆ (เพื่อให้ออกแบบ Flow ให้ตรง)

| Flow ตอบ | แอปทำอะไร |
|---|---|
| 200 + `fileUrl` ถูกต้อง | สำเร็จ เก็บลิงก์ |
| 429 หรือ 503 | retry สูงสุด 2 ครั้ง (รอ 1 วินาที แล้ว 3 วินาที หรือตาม `Retry-After` สูงสุด 10 วินาที) ด้วย `requestId` เดิม |
| 401 / 403 | หยุด แจ้งให้ตรวจคีย์และสิทธิ์ |
| 404 | หยุด แจ้งว่าไม่พบ Flow (URL เก่าหรือ Flow ถูกปิด) |
| 400 / 500 / อื่น ๆ ≥ 400 | หยุด แสดงสถานะและข้อความ `error` |
| 502 / 504 / เกินเวลา / การเชื่อมต่อหลุด | **ไม่ retry** แจ้งว่าไฟล์อาจถูกสร้างไปแล้ว ให้ตรวจไลบรารีก่อนส่งซ้ำ |
| 200 แต่ไม่มี `fileUrl` | **ไม่ retry** แจ้งว่ารูปแบบคำตอบไม่ถูกต้อง |

เวลารอของแอปตั้งที่ `POWER_AUTOMATE_TIMEOUT_SECONDS` (ค่าเริ่มต้น 120) ต้องตรวจเพดานเวลาตอบแบบซิงโครนัสของ Flow ในเอกสาร Microsoft ปัจจุบัน ถ้า Flow ตอบเร็วสุดช้ากว่าค่านี้ แอปจะถือว่าเกินเวลา

## 2. Flow 2: ส่งแถวเข้า Master-List

### 2.1 รอ IT ตอบ

> **รอ IT ตอบ (`02_S0_IT_REQUEST.md` ข้อ 6)** ก่อนลงมือส่วน 2.3 ต้องรู้:
> 1. ปลายทางคืออะไร: **SharePoint List** หรือ **ไฟล์ Excel (ตารางในไฟล์) บน SharePoint** หรืออื่น ๆ
> 2. ใช้ Flow ตัวที่ 2 แยก (ตามคู่มือนี้) หรือขยาย Flow 1
> 3. ฟิลด์ที่ต้องการครบ 13 ฟิลด์หรือไม่ และชื่อคอลัมน์ปลายทาง
> 4. ยืนยันให้ Flow 2 กันแถวซ้ำด้วย `requestId`
>
> ส่วน 2.1–2.2 (trigger/schema/response) ตรงกับโค้ดแล้ว ทำก่อนได้ ส่วน 2.3 (ขั้นตอนบันทึก) แยกเป็นสองทางตามคำตอบ

### 2.2 Trigger และ schema (ตรงกับโค้ด)

สร้าง Flow ใหม่ด้วย **When an HTTP request is received** ตั้งค่าเหมือนหัวข้อ 1.2 (Concurrency = 1, แจ้งเตือนเมื่อล้ม) แล้วใส่ schema:

```json
{
  "type": "object",
  "properties": {
    "requestId": { "type": "string" },
    "record": {
      "type": "object",
      "properties": {
        "date":            { "type": ["string", "null"] },
        "vendor":          { "type": ["string", "null"] },
        "category":        { "type": ["string", "null"] },
        "total_price":     { "type": ["number", "string", "null"] },
        "invoice_status":  { "type": ["string", "null"] },
        "tel":             { "type": ["string", "null"] },
        "tax_id":          { "type": ["string", "null"] },
        "pr_run_no":       { "type": ["string", "null"] },
        "pr_request_date": { "type": ["string", "null"] },
        "qt_no":           { "type": ["string", "null"] },
        "description":     { "type": ["string", "null"] },
        "unit_price":      { "type": ["number", "string", "null"] },
        "sharepoint_url":  { "type": ["string", "null"] }
      }
    }
  },
  "required": ["requestId", "record"]
}
```

ตัวอย่างคำขอจริง (ค่าสมมติ):

```json
{"requestId": "9c1d7e52-2b4a-4f0e-a6d3-5e8b1c7f0a24",
 "record": {"date": "2026-03-19", "vendor": "บริษัท ตัวอย่าง จำกัด", "category": "อุปกรณ์", "total_price": 12345.5,
            "invoice_status": "Completed", "tel": "0200000000", "tax_id": "0000000000000", "pr_run_no": "PR-0001",
            "pr_request_date": "2026-03-01", "qt_no": "QT-0001", "description": "ตัวอย่างรายการ",
            "unit_price": 12345.5, "sharepoint_url": null}}
```

- ฟิลด์ที่ไม่มีค่าส่งเป็น `null` เสมอ ครบ 13 ฟิลด์ (ชนิดของแต่ละฟิลด์ในตารางจริงอาจเป็นตัวเลขหรือข้อความ จึงเปิดกว้างไว้ ให้ปลายทางแปลงเอง)
- ไม่มีไฟล์ ไม่มี path ในเครื่อง ไม่มีรหัสแถวภายในของแอป
- แอปส่งเฉพาะ **แถวใหม่** ครั้งละแถว ไม่ส่งซ้ำตอนแนบไฟล์เข้าแถวเดิม
- `requestId` สร้างใหม่ต่อการส่ง 1 แถว และเท่ากันทุกครั้งที่ retry (เฉพาะ 429/503)
- header `X-Api-Key` ตรวจเหมือนหัวข้อ 1.3 ขั้น 1 (ไม่บังคับ แต่แนะนำ) โดยใช้ **คีย์ของ Flow 2 คนละชุดกับ Flow 1**

### 2.3 ขั้นตอนบันทึก (ขึ้นกับคำตอบของ IT)

ลำดับรวมเหมือนกันทั้งสองทาง: ตรวจคีย์ → ตรวจ `requestId` ซ้ำ → บันทึก → จด `requestId` → Response

**ทาง A: SharePoint List** (ถ้าปลายทางเป็นลิสต์)
- สร้างลิสต์ทดสอบที่มีคอลัมน์ตรงกับ 13 ฟิลด์ (ชนิดวันที่/ตัวเลข/ข้อความให้ตรง และตัดสินใจเรื่องค่า `null`)
- ใช้ action **Create item** แมปฟิลด์จาก `triggerBody()?['record']?['<ชื่อฟิลด์>']`
- วิธีกันซ้ำที่ง่ายที่สุด: เพิ่มคอลัมน์ `RequestId` (ข้อความ, ตั้ง Enforce unique values) ในลิสต์เดียวกัน แล้ว Get items ด้วย filter `RequestId eq '<requestId>'` ก่อนสร้าง

**ทาง B: ไฟล์ Excel บน SharePoint** (ถ้าปลายทางเป็นตารางในไฟล์)
- ข้อมูลต้องจัดเป็น **Table** ในไฟล์ (ไม่ใช่ช่วงเซลล์ธรรมดา) ใช้ action **Add a row into a table** แมปฟิลด์เป็นคอลัมน์
- Excel ไม่มีค่าไม่ซ้ำให้ใช้ ต้องมีคอลัมน์ `RequestId` ในตารางและใช้ **List rows present in a table** กรองก่อน หรือใช้ลิสต์กันซ้ำแยกต่างหากตามหัวข้อ 3
- ระวัง: ไฟล์ Excel ถูกล็อกเมื่อมีคนเปิดแก้อยู่ ทำให้ Add a row ล้ม แจ้งผู้ใช้ไม่ให้เปิดไฟล์ค้างไว้ (Concurrency = 1 ช่วยกันคำขอของแอปชนกันเอง แต่ไม่ช่วยเรื่องคนเปิดไฟล์)

> ถ้า IT ตอบว่าปลายทางเป็นอย่างอื่น ให้บอกผู้พัฒนา แอปไม่ผูกกับชนิดปลายทาง รูปแบบคำขอ/คำตอบเดิมใช้ได้ทุกแบบ

### 2.4 Response

สำเร็จ (Status 200, `Content-Type: application/json`): `{"ok": true}` (จะใส่ `itemUrl` เพิ่มก็ได้ แอปไม่ใช้)
คำขอซ้ำที่เคยสำเร็จแล้ว (`requestId` เดิม): ตอบ `{"ok": true}` เหมือนกัน ไม่สร้างแถวซ้ำ
ล้มเหลว: 4xx/5xx พร้อม `{"error": "ข้อความสั้น ๆ"}`

กติกาแอป: **สำเร็จเมื่อ `ok` เป็นค่า `true` เท่านั้น** (ข้อความ `"true"`, เลข `1` หรือไม่มี `ok` ถือว่าไม่สำเร็จ)

### 2.5 สิ่งที่แอปทำเมื่อ Flow 2 ตอบแบบต่าง ๆ

| Flow ตอบ | แอปทำอะไร |
|---|---|
| 200 + `{"ok": true}` | สำเร็จ |
| 429 / 503 | retry สูงสุด 2 ครั้ง ด้วย `requestId` เดิม |
| 401 / 403 / 404 | แจ้งตรวจคีย์/สิทธิ์ หรือ URL |
| อื่น ๆ ≥ 400 หรือ `error` | แจ้งข้อความ ไม่ retry |
| 502 / 504 / เกินเวลา / เชื่อมต่อหลุด / 200 แต่ไม่มี `ok: true` | **ไม่ retry** แจ้งว่ารายการอาจถูกสร้างใน Master-List ไปแล้ว ให้ตรวจก่อนส่งซ้ำ |

ทุกกรณีที่ล้ม **การบันทึกในแอปไม่ล้มตาม** (แถวและไฟล์ในเครื่องอยู่ครบ) หน้าสรุปหลังอัปโหลดแจ้งจำนวนแถวที่ส่ง Master-List ไม่สำเร็จ ตอนนี้ **ยังไม่มีปุ่มส่งแถวนั้นซ้ำ** และแอปไม่เก็บสถานะส่งแล้ว/ยังต่อแถว แถวที่ส่งล้มต้องเติมใน Master-List ด้วยมือ

เวลารอ: `MASTERLIST_TIMEOUT_SECONDS` (ค่าเริ่มต้น 30 เพราะส่งแค่ข้อความ)

ปลายทางที่เป็น `http://` ไป IP ภายในบริษัท: แอปปฏิเสธตามค่าเริ่มต้น (บังคับ https) ถ้าจำเป็นต้องทดสอบให้ตั้ง `MASTERLIST_ALLOW_HTTP=1` (รับเฉพาะ 10.x / 172.16-31.x / 192.168.x และเฉพาะ Master-List) ข้อมูลและ `X-Api-Key` จะไม่ถูกเข้ารหัส ใช้กับปลายทางทดสอบเท่านั้น ก่อนใช้จริงต้องเปลี่ยนเป็น https

## 3. การกันซ้ำด้วย requestId (ใช้กับทั้งสอง Flow)

เหตุผล: ถ้าแอป retry (429/503) หรือผู้ใช้ส่งซ้ำหลังเกิน timeout Flow อาจได้คำขอเดิมสองครั้ง แอปส่ง `requestId` เดิมทุกครั้งที่ **retry ภายในการส่งครั้งเดียว** เพื่อให้ Flow รู้ว่าเป็นของเดิม

สิ่งที่ต้องทำใน Flow:
1. มีที่เก็บ `requestId` ที่ทำสำเร็จแล้ว เช่น SharePoint List ชื่อ `ProcessedRequests` คอลัมน์ `Title` = `requestId` (ตั้ง Enforce unique values), `ResultUrl` = ลิงก์ที่ตอบไป (Flow 1) หรือเว้นว่าง (Flow 2), และวันที่บันทึก แยกลิสต์กันระหว่าง Flow 1 และ Flow 2 หรือเพิ่มคอลัมน์ `Flow`
2. ต้นทางของ Flow: Get items ด้วย filter `Title eq '<requestId>'`
   - เจอ → ตอบผลเดิมทันที (Flow 1: `fileUrl` เดิม, Flow 2: `{"ok": true}`) **ไม่สร้างซ้ำ**
   - ไม่เจอ → ทำงานต่อ
3. ท้าย Flow หลังสร้างสำเร็จ: Create item ใน `ProcessedRequests`
4. Concurrency ของ trigger = 1 (กันสองคำขอที่ `requestId` เดียวกันเข้าพร้อมกันแล้วผ่านการเช็กทั้งคู่)
5. ลบรายการเก่าใน `ProcessedRequests` ตามนโยบาย (เช่นเก็บ 30 วัน) เพราะ `requestId` ไม่ถูกใช้ซ้ำข้ามการส่งคนละครั้ง

**ข้อจำกัดที่ต้องรู้:** `requestId` ใหม่ทุกครั้งที่ผู้ใช้อัปโหลดหรือส่งใหม่ ดังนั้น **กันได้เฉพาะคำขอซ้ำจาก retry ของการส่งเดียวกัน** ไม่กันกรณีผู้ใช้อัปโหลดไฟล์/แถวเดิมซ้ำอีกรอบ (แอปยังไม่มีการเก็บ id ข้ามครั้ง ตัดสินใจหลัง IT ยืนยันว่ากันซ้ำด้วย `requestId` ใช้ได้จริง ดู `03_PENDING_ACTIONS.md`)

กรณี timeout/502/504 แอป **ไม่ retry เอง** แม้ Flow กันซ้ำได้ เพราะยังไม่มีปุ่มส่งซ้ำ จึงต้องตรวจปลายทางด้วยมือ

## 4. ค่าใน `.env` ฝั่งแอป (ผู้ดูแลแอปเป็นคนใส่ ตัวอย่างต่อไปนี้เป็นค่าสมมติทั้งหมด)

ห้ามใส่ค่าจริงในเอกสาร/แชต/Git ไฟล์ `.env` ตั้งสิทธิ์ `chmod 600` แล้วรีสตาร์ทแอปหลังแก้

```
STORAGE_BACKEND=powerautomate

# Flow 1 ส่งไฟล์
POWER_AUTOMATE_UPLOAD_URL=https://example.invalid/flow1-placeholder
POWER_AUTOMATE_API_KEY=ตัวอย่าง-คีย์-flow1
POWER_AUTOMATE_TIMEOUT_SECONDS=120
POWER_AUTOMATE_MAX_FILE_MB=50

# Flow 2 ส่งแถว Master-List
MASTERLIST_API_URL=https://example.invalid/flow2-placeholder
MASTERLIST_API_KEY=ตัวอย่าง-คีย์-flow2
MASTERLIST_TIMEOUT_SECONDS=30
```

- URL ต้องขึ้นต้น `https://` (แอปปฏิเสธ http ยกเว้นเครื่องตัวเองเพื่อทดสอบ) และแอปไม่ตาม redirect
- คีย์ต้องเป็นตัวอักษร ASCII ธรรมดา ห้ามมีการขึ้นบรรทัดใหม่/แท็บ
- ถ้าไม่ตั้ง `MASTERLIST_API_URL` แอปข้ามการส่ง Master-List และไม่เตือนซ้ำทุกครั้ง
- Flow 1 และ Flow 2 ใช้ URL คนละอัน ห้ามใช้ซ้ำกัน

## 5. ทดสอบหลังสร้าง (ใช้ที่ว่างเท่านั้น)

### 5.1 Flow 1 ด้วย `scripts/check_flow.py`

ผู้ดูแลแอปตั้ง `.env` (ชี้ไลบรารี **ว่าง**) แล้วรันในโฟลเดอร์โปรเจกต์:

```
venv/bin/python scripts/check_flow.py
```

สคริปต์ส่งไฟล์ข้อความเล็ก ๆ 1 ไฟล์ (ไม่มีข้อมูลจริง) ไปโฟลเดอร์ `_connection_test` เท่านั้น พิมพ์ชื่อเซิร์ฟเวอร์และลิงก์ที่ Flow ตอบ ไม่พิมพ์ URL เต็มหรือคีย์ ผลที่ถูกต้อง: ขึ้น "สำเร็จ", ไฟล์อยู่ใน `_connection_test` จริง, ลบไฟล์ทดสอบทิ้งเอง
ถ้าล้ม ข้อความภาษาไทยบอกเหตุ (ตั้งค่าไม่ครบ/คีย์ไม่ถูก/ไม่พบ Flow/ตอบรูปแบบผิด ฯลฯ) ดูตารางหัวข้อ 1.5

### 5.2 Flow 2

`scripts/check_flow.py` **ไม่ครอบคลุม Flow 2** (ตั้งใจไม่ให้ส่งข้อมูลแถวไปปลายทางจริงโดยไม่จำเป็น) ทดสอบได้สองวิธี และใช้ปลายทาง **ทดสอบที่ว่าง** เท่านั้น:

1. **ทดสอบ Flow ตรง ๆ** ส่งคำขอตัวอย่างจากหัวข้อ 2.2 ไปที่ URL ของ Flow 2 ด้วยเครื่องมือยิง HTTP ที่ IT ใช้ (เช่น Postman) ใส่ header `X-Api-Key` และ `Content-Type: application/json` ตรวจว่าได้ `{"ok": true}` และมีแถวใหม่ 1 แถวในปลายทางทดสอบ แล้วส่ง `requestId` เดิมซ้ำ ต้องได้ `{"ok": true}` และ **ไม่เกิดแถวที่สอง** (ไม่ควรวาง URL จริงในประวัติคำสั่งของเทอร์มินัล)
2. **ทดสอบผ่านแอปบนสำเนา** ผู้ดูแลแอปรันแอปสำเนาที่ใช้ฐานข้อมูลทดสอบ (ไม่ใช่ข้อมูลจริง) ตั้ง `MASTERLIST_API_URL` ชี้ Flow 2 แล้วอัปโหลด PR ปลอม 1 ไฟล์ ตรวจว่าแถวขึ้นในปลายทางทดสอบ และหน้าสรุปไม่เตือนว่าส่งไม่สำเร็จ

### 5.3 กรณีล้มที่ต้องลอง (ทั้งสอง Flow)

| กรณี | วิธีลอง | ผลที่ต้องเห็นฝั่งแอป |
|---|---|---|
| คีย์ผิด | ตั้งคีย์ในแอปให้ต่างจาก Flow | แจ้ง "Flow ปฏิเสธการเรียก" ไม่เห็นคีย์ในข้อความ |
| Flow ถูกปิด | ปิด (Turn off) Flow ชั่วคราว | แจ้งไม่พบ Flow/ปฏิเสธ ตามสถานะที่ได้ แถวและไฟล์ในเครื่องยังอยู่ |
| ตอบช้าเกินเวลา | ใส่ Delay ใน Flow เกิน timeout ของแอป (ลด `*_TIMEOUT_SECONDS` เพื่อไม่ต้องรอนาน) | แจ้งหยุดรอ และเตือนให้ตรวจปลายทางก่อนส่งซ้ำ ไม่ retry |
| Flow ถูกจำกัดอัตรา | ให้ Flow ตอบ 429 หรือ 503 (หรือส่งถี่ ๆ) | แอป retry แล้วสำเร็จ หรือหยุดหลัง 2 ครั้ง ปลายทางต้องไม่มีของซ้ำ |
| ตอบผิดรูปแบบ | ให้ Response ตอบ 200 แต่ไม่มี `fileUrl` (Flow 1) หรือ `ok` (Flow 2) | แจ้งรูปแบบไม่ถูกต้อง ไม่ retry |
| ตอบ `error` | ให้ Flow ตอบ `{"error":"ทดสอบ"}` | แจ้งข้อความทดสอบ ไม่เห็น URL/คีย์ |
| `requestId` ซ้ำ | ส่งคำขอเดียวกันสองครั้งเพราะข้อ 5.2 วิธี 1 | ผลเดิม ไม่สร้างซ้ำ |
| ชื่อไฟล์ไทย / มีอักขระพิเศษ (Flow 1) | อัปโหลดไฟล์ชื่อไทย และชื่อมี `# % :` | ชื่อไฟล์ใน SharePoint ถูกต้อง (อักขระต้องห้ามกลายเป็น `_`) |
| ชื่อไฟล์ซ้ำ (Flow 1) | ส่งไฟล์ชื่อเดียวกันลงโฟลเดอร์เดียวกัน 2 ครั้งต่างเนื้อหา | ตามที่ตกลงกับ IT (ทับ/ปฏิเสธ) ไม่ล้มแบบอ่านไม่รู้เรื่อง |
| โฟลเดอร์มีอยู่แล้ว (Flow 1) | ส่งไฟล์ที่สองเข้าโฟลเดอร์เดิม | สำเร็จ ไม่ error เรื่องโฟลเดอร์ซ้ำ |
| ไฟล์ใหญ่ (Flow 1) | ส่งไฟล์ใกล้เพดาน (เช่น 20, 40, 50 MB ของปลอม) | สำเร็จ หรือล้มด้วยข้อความชัดเจนก่อนถึงเพดานที่ตั้ง |
| ส่งหลายไฟล์แล้วล้มกลางชุด (Flow 1) | ปิด Flow ระหว่างส่งหลายไฟล์ | แอปหยุดและบอกว่าไฟล์ไหนส่งแล้ว/ยังไม่ส่ง |
| Flow 2 ล้ม แต่ Flow 1 สำเร็จ | ปิดเฉพาะ Flow 2 | ไฟล์ขึ้น SharePoint, แถวบันทึกในแอป, หน้าสรุปเตือน Master-List ส่งไม่สำเร็จ |
| Excel ถูกเปิดค้าง (Flow 2 ทาง B) | เปิดไฟล์ปลายทางแก้อยู่ แล้วส่งแถว | Flow ตอบ error ชัดเจน (ไม่ค้าง) แอปแจ้งส่งไม่สำเร็จ |

เมื่อลองครบแล้ว ลบไฟล์/แถว/รายการทดสอบทั้งหมดออกจากปลายทางทดสอบ
